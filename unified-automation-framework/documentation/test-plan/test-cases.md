# Test Cases

Every automated test, with its preconditions, test data, steps and expected results. The test code is the executable version of each entry, and the file is named under each heading. Assertions are listed under **Expected results**: each bullet is checked by at least one `expect`.

- **Format:** the test ID is the first word of the test's title, so it appears in every report (see [reporting](../framework-guide/reporting-and-logs.md#test-ids)).
- **Tags:** `@smoke` marks the minimum set to run after a deployment: `npx playwright test --grep @smoke`.

## Shared preconditions

Referred to by code below.

| Code | Precondition | Provided by |
|---|---|---|
| **P-APP** | ShopLite is running and `GET /api/health` returns 2xx | `app-health` setup project (fails the run otherwise) |
| **P-DATA** | Test data older than 60 minutes removed; every catalogue product has stock ≥ 50 | `test-data` setup project |
| **P-DB** | Database credentials configured (`DB_*`) | `.env` locally, GitHub Secrets in CI |
| **P-CUST** | A new customer, generated by `aCustomer()`, registered and logged in through the API, used by this test only, and deleted (with their carts and orders) after the test | `customerAccount` fixture |
| **P-SIGNED** | P-CUST, and the browser starts already signed in as that customer (token placed in the page's storage, no UI login) | `signedInTest` fixture |
| **P-MOB** | Android emulator running, My Demo App 2.3.0 installed, app data cleared and app relaunched before the test | `wdio.conf.ts`, `MyDemoApp.freshStart()` |

**Products** are picked at random from the live catalogue among those with enough stock (`pickProduct`). They are never hard-coded. Expected names, prices and totals come from the catalogue data, and the framework's `Money` and `OrderPlan` calculate the amounts independently.

## Web UI (Chromium, Firefox, WebKit)

### WEB-AUTH-001 Registered customer logs in with valid credentials `@smoke`
`tests/web/auth.spec.ts`
- **Description:** A registered customer can log in through the login form.
- **Preconditions:** P-APP, P-DATA, P-CUST (not signed in)
- **Test data:** The P-CUST customer's generated email and password.
- **Steps:** 1. Open `/login`. 2. Enter the email and password and submit.
- **Expected results:**
  - The browser is on the catalogue (`/`).
  - The header greets the customer: "Hi, <first name>".
  - The Logout button is visible and the Login link is hidden.

### WEB-AUTH-002 Login is rejected for a wrong password
`tests/web/auth.spec.ts`
- **Description:** A wrong password does not log the customer in.
- **Preconditions:** P-APP, P-DATA, P-CUST

- **Expected results:**
  - The error shows "Email or password is incorrect".

## API

All API tests also check each response against its JSON schema (`toMatchSchema`). Error responses must match the error schema `{ error: { code, message, details? } }`.

### API-CUSTOMER-001 Create a customer `@smoke`
`tests/api/customers.spec.ts`
- **Description:** `POST /api/customers` registers a customer, and the new credentials work.
- **Preconditions:** P-APP
- **Test data:** A generated customer with an **upper-case** email and the phone `+1 555 010 0199`.
- **Steps:** 1. POST the customer. 2. POST `/api/auth/login` with the same credentials.
- **Expected results:**
  - 201, and the body matches the customer schema. Email is stored lower-case. First name, last name and phone are as sent. `createdAt` = `updatedAt`.
  - The `Location` header is `/api/customers/<id>`.
  - Login returns 200, the session schema, and the same customer ID.
- **Cleanup:** the customer is deleted.

### API-CUSTOMER-002 Retrieve the logged-in customer
`tests/api/customers.spec.ts`
- **Description:** A customer can read their own record by ID and through `/auth/me`.
- **Preconditions:** P-APP, P-CUST
- **Steps:** 1. `GET /api/customers/<own id>` with the token. 2. `GET /api/auth/me`.
- **Expected results:**
  - Both return 200 with the customer schema.
  - Both bodies equal the customer from the login session.

### API-CUSTOMER-003 Update a customer with PUT and PATCH
`tests/api/customers.spec.ts`
- **Description:** PUT replaces the profile, PATCH changes only the fields sent, and the email can't be changed.
- **Preconditions:** P-APP, P-CUST
- **Test data:** Grace / Hopper / `+44 20 7946 0000`, then the last name Hopper-Murray, then no phone, then a new email.
- **Steps:** 1. PUT the full profile. 2. PATCH the last name. 3. PUT without a phone. 4. PATCH the email.

  2. 200, only the last name changed.
  3. 200, phone is `null` (full replacement).
